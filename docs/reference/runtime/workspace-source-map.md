## Generic compilation and isolation split

The reusable spine stops at explicit ports; it does not make engineering methods or
solver transports generic:

```text
project technical tools
  -> exact basis/source readers
  -> pure technical compiler
  -> review-draft CAS -> MRTR -> provider-free admission capture
  -> vertical-owned execution review + registered specialized executor
       -> IsolatedCodeRunner
            -> fail-closed broker
                 -> EphemeralExecutionBackend (replaceable isolated lifecycle)
                 -> code-owned output validator (replaceable by declared format)
                 -> publication-gated output CAS
       -> vertical-owned WAL + documentary evidence
       -> separate canonical-promotion operation, when implemented
```

Build123d is the first qualified compiler/isolation consumer of that spine. It binds the
qualified Python subset, Microsandbox local 0.6.8 OCI/microVM backend, AP214/OCCT
validator, filesystem output CAS and Build123d attempt/evidence contracts. The neutral
backend port remains replaceable in code, but the product composition registers one
local backend: there is no caller-selectable runtime menu, Deno Deploy route,
`@deno/sandbox` route or remote control plane. `deno task verify:generic:core` proves
the runner seam with a second, non-Build123d JSON fixture; it does not qualify that
fixture or generalize the fixed Build123d wrapper, profile, executor, WAL or evidence.

The server-owned profile pins the OCI image digest, direct executable and wrapper,
paths, isolation policy, AP214 manifest, OCCT validator and `proven` teardown threshold.
The adapter rejects native runtime overrides; resolves the code-owned empty config,
native module, `msb` executable and `libkrunfw` inside the pinned platform package; and
verifies their SHA-256 before loading. Unsupported hosts fail closed. It uses no shell,
allows no image pull, and checks the observed image and post-create microVM
configuration. Network is disabled with deny-all ingress/egress, no ports, nameservers,
secrets or host CA trust. The VM receives only the admitted source bytes; it has no
repository, Docker socket, canonical evidence volume or caller-provided environment. The
broker alone inventories declared outputs, validates them outside the VM, commits them
to CAS and releases them after run-labelled removal plus a zero-remaining-sandbox check.

Modelica `modelica-closed-subset-v2` is the second compiler profile. Product execution
reopens that admission through `ReopenAdmittedCompilationSource` and
`simulate.run-admitted-modelica@1`. Pattern:
[admitted source isolated execution](../pipeline/admitted-source-isolated-execution.md). CalculiX
still has no agent-authored compiler profile: the agent never writes `.inp`.

The Modelica kit remains a separate image-smoke authority. Its qualification capture is
`d6aee5fe375daa55cec29a32acf27181dd4bb8ea8e5c3f90f848cc718c149428` for exact image
`casys/modelica-microsandbox-worker@sha256:7d3fdeabe794b0ded5360921b16724c7904487e9d11bc24fa37c72f9b92a1894`.
The real generation-0 microVM run validated OpenModelica 1.27.0 / MSL 4.1.0 output
`temperature_final = 22 degC`, publication reread after an adapter restart and proven
destruction. That authority covers only `linear-thermal-ramp-v1@0.1.0` with
`linear-ramp-nominal`; it is not admitted `.mo`. The
`simulate.run-qualified-modelica-kit@1` descriptor and fail-closed dispatcher entry stay
registered in every composition. Explicit loopback `--local-execution` makes kit review
and executor available by composing the exact runtime and pinned qualification. The same
flag composes admitted Modelica on the same image **family** with different backend
args. Kit `@1` has no ROP or provider fallback and publishes three documentary artifacts
plus the one conformance observation, not a product verdict.

The real CalculiX generation-0 gate passed against
`casys/calculix-microsandbox-worker@sha256:9b3a7468bfbc3f0fe27f7a9ac17c0eb72f1925968173e5a01d985cfa19cbc0a2`.
It reread all nine CAS outputs, validated a 5,713-node / 22,362-element mesh, checked
`0.0761 mm <= 5 mm` maximum displacement and `0.723 MPa <= 90 MPa` maximum von Mises
stress, replayed the exact evidence and proved destruction. The post-lease rerun also
proved one claimant and one worker dispatch across concurrent calls, with identical
evidence replay. The `verify.run-fea-static-proof@3` descriptor and fail-closed
dispatcher entry also stay registered in every composition. Its concrete executor
becomes available only under explicit loopback local execution when SysON is also
available. It requires an exact `@3` ROP2, journals the SysON oracle after local
evidence is durable, and publishes the nine local outputs plus isolated-execution and
SysON evidence.

Existing recorded-analysis `@1/@2` operations retain their separate capability ports,
provider MCP adapters, plans and WALs. They remain composed through their provider
routes where configured and are never redirected to the two local executors. In
particular, CalculiX `@3` rejects an `@2` ROP before execution, while the fixed Modelica
kit neither adopts provider scenarios nor replaces their historical records.

SysON also remains outside the local sandbox. Architecture, requirements and evaluation
executors call its private MCP through their own WAL and exact readback contracts, then
publish only reviewed Thread evidence. The local microVM is a compute boundary, not a
replacement provider, evidence store or decision authority.

At the Build123d seam, `server.ts` applies three explicit states. With no
`build123dExecution`, it exposes no review tool and the registered dispatcher reports
the operation unavailable. A profile alone exposes the provider-free review tool but
still no executor. A complete profile plus exact empty runtime marker composes the local
Microsandbox backend, broker and
[`file-isolated-output-cas.ts`](../../../src/adapters/shared/cas/file-isolated-output-cas.ts),
then connects the WAL, evidence stores and executor to the registered-run dispatcher.
The bounded state lives under
`${recordedAnalysisDirectory}/build123d/{outputs,attempts,drafts,captures}`. The output
CAS owns the run-and-producer-generation tri-state publication marker and exposes no
digest-only reader. One recovery redispatch keeps the logical execution run id, closes
generation 0, persists the only allowed `0 -> 1` advance and consumes it once; no
generation 2 exists. Composition performs no network or microVM I/O; only a subsequently
reviewed run can reach execution. Targeted composition/register tests cover these three
states. The final real gate passed against
`casys/build123d-microsandbox-worker@sha256:0e19aee61aaab326ec29e50753a0ef56432d255fb44fd21c40988e90ff7601f8`:
it ran producer generation 0 in the local microVM, validated a 15,430-byte AP214 STEP
with OCCT, proved broker destruction, resolved the publication as `published` and reread
the CAS. It correctly performed no recovery abort after publication. It did not exercise
generation-1 recovery, run a persisted project executor or activate production.

Even after executor composition, its output remains a noncanonical review draft. A
successful executor write adds exactly one JSON `build123d-execution-capture/1.0`
document and its verified admission consumption to the successor Thread, never a STEP or
canonical geometry artifact. The existing `design.write-geometry@1` belongs to the
historical MCP sandbox-preview path; promotion from the isolated-output CAS requires a
future separate operation and human MRTR. Its tools and already persisted items/state
remain present until a separately reviewed migration and removal; the local vertical
does not reinterpret them. CPU-time and process-count ceilings also remain explicitly
unattested even though wall-time, memory, output caps and cleanup have stronger
evidence. Native N-API calls are not cancellable once entered; a privileged same-host
race remains possible between native-artifact hashing and import; and guest directory
listing is materialized within the SDK protocol frame rather than paginated by the
adapter. These are explicit host trust/availability limits, not extra agent
capabilities.
