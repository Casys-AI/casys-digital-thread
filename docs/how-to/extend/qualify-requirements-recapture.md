# How-to: qualify requirements recapture

Audience: maintainers · Diátaxis: how-to · Kind: runbook

Status: **qualified local generic recapture route**. Not a release, physical proof or
general SysML coverage claim.

The ID01 refusal after monotone architecture enrichment established a missing generic
authority: an unchanged native requirements declaration cannot be rebound by the
insertion-only `model.write-requirements@1`, and the compilation resolver correctly
refuses an active requirements capture on a different architecture. The human authorized
this separate operation on 2026-09-07. Do not weaken either existing guard.

## Single authority and bounded meaning

The new operation identity is `model.recapture-requirements@1`: provider-read-only
recapture of one existing generic integer-scalar requirements family. This is distinct
from both renderer mutation and agent-authored documentary SysML. It publishes Thread
evidence after a new exact MRTR; it never inserts, deletes, repairs or evaluates SysON
elements. Provider tools, arguments, queries and runtime remain server-owned.

The server must derive a closed review from the unique current Thread tip, its exact
architecture and seed, and the unique active requirements predecessor for one target.
The target is an already sealed reusable PartDefinition, not an occurrence or a label
substitution. The approved envelope binds the operation, Thread basis, architecture,
predecessor, target and complete unchanged requirements. A stale review is refused.

Accept only `requirements-capture/3.0` produced by `model.write-requirements@1`, or
`requirements-capture/4.0` produced by `model.recapture-requirements@1`, when the
complete artifact/CAS/producer/lineage is proven. Reopen the historical architecture
against which it was captured; then prove the target survives unchanged in the current
monotone architecture. Do not reinterpret old bytes as a new schema. Schemas 1.0 and 2.0
remain refused.

Recapture must reread the exact native RequirementUsage, its ownership, the unique
subject and subject typing, the exact ConstraintUsage set, and extracted metric,
operator, integer threshold and qualified unit. Every captured native requirement and
constraint identity must survive. If the prior schema did not seal the subject UUID,
record its newly observed exact identity without claiming historical UUID continuity.
The existing supported units and safe-integer threshold grammar are unchanged. No
dimensions, loads, criteria or defaults are invented by this operation.

Refuse missing/duplicate predecessors, foreign targets, stale or ambiguous architecture,
replacement, removal, additional constraints, changed values/units/operators, malformed
native responses, unknown review fields, or an unresolved writer sibling. Same-basis
no-op recapture is not an enrichment or a repair route. No batch or recursive recapture,
arbitrary SysML, caller-selected runtime, solver call, or automatic ancestor update is
included.

## Implementation and proof chain

1. Trace the requirements writer and exact parser, PartDefinition read-only capture and
   durable publication recovery, operation registry, review/approval/dispatch,
   capability admission, compilation basis and requirements consumers.
2. Add the distinct registered operation, closed server-derived review and exact MRTR
   validation. Bind the composed inspection capability; absence stays unavailable.
3. Publish a distinct versioned requirements capture for read-only recapture, with its
   exact predecessor and current architecture references. Retain historical captures and
   use the same requirement family URI namespace for unambiguous active-tip selection.
   Never label a read as `syson_element_insert_sysml`.
4. Atomically supersede only the target family. Preserve historical entities and archive
   their downstream active requirement evaluations/violations through the existing
   archive cascade. Newly traced requirements receive no inherited verdict. Preserve
   unrelated families and evidence.
5. Persist and reopen an operation-specific publication record before attachment. A
   saved capture or completed publication must replay without a second provider read; an
   uncertain local publication must not silently generate a different successor. There
   is no native write to retry and no write acknowledgement to fabricate.
6. Update consumers through exact schema/operation/producer discrimination. Keep old
   schema-3 writer evidence valid and reject forged cross-kind producers, broken
   historical lineage and mismatched current bases. Prove future legitimate writer
   enrichment can consume an exact recapture predecessor without weakening its ratchet.
7. Test accepted, refusal, ambiguity, stale MRTR, no-op, replay, publication failure and
   requirements/evaluation supersession paths. Run focused source and documentation
   gates. Fixture readback is not native runtime evidence.
8. In the real composed runtime, execute review → MRTR → queue → readback → CAS → Thread
   successor, then completed replay with no new dispatch. Rerun the exact previously
   refused compilation preview against the fresh basis. Record each result separately.

## Local qualification observed on 2026-09-07

Native Grok implemented the bounded slice; Astra reviewed the actual diff and
independently ran 16 focused test files in the isolated candidate checkout: **274
passed, 0 failed**. After explicit integration, type checking, scoped formatting/lint
and 58 registry/composition/boundary tests passed in the main checkout. These checks
cover exact producer/seed/architecture lineage, native identities, refusal, publication
uncertainty, completed replay, future writer enrichment, compiler, FEA seal and
Workbench consumers. Fixture provider-read counts remain source-test evidence.

The composed local YOLO runtime then recaptured ID01's unchanged CameraMountBracket
requirements from Thread r70 to r71. The PartDefinition, RequirementUsage and
ConstraintUsage UUIDs and the `camera_bracket_bench_max_von_mises_pa <= 260000000 Pa`
criterion were preserved. Schema 3 had not sealed the subject UUID: schema 4 records the
newly observed subject without claiming historical subject-UUID continuity. The old
capture bytes remain unchanged; old Thread requirement/evaluation entities are archived
and the new requirement has no evaluation. Completed public replay returned the same
project r504 / Thread r71 and same capture, with no second publication.

The exact basis resolver still rejects historical r70, while r71 resolves 110 elements.
CentralDeck source revision 2, attachment revision 5 at workspace 116, then compiled
without gaps and was admitted at Thread r72. This closes the previously observed
requirements-basis refusal; it does not claim a subsequent CAD export succeeded. Exact
identities are in the
[ID01 recapture ledger](../../annex/project-dossiers/inspection-drone-id01/requirements-recapture-20260907.md).

This qualification proves current unchanged requirements and their exact basis, not
mechanical resistance, a new solver result, compliance or fitness for flight. A physical
verdict needs its own fresh evaluation against the new requirements. No release or
provider image change was performed.

## Consumer regression covered by this qualification

The FEA seal reviewer selects the exact active family tip before matching preserved
native target and RequirementUsage identities. A normal predecessor/successor pair is
not ambiguous; historical reads remain available and genuinely multiple active tips are
refused. The regression includes both old and new captures in the same snapshot.

The Workbench requirements enricher and FEA seal executor discriminate the exact
writer/schema-3 and recapture/schema-4 pairs together with the shared parser. New Thread
requirement IDs must derive from the new capture digest. Native UUID continuity does not
permit reusing old Thread requirement IDs or evaluation verdicts.
