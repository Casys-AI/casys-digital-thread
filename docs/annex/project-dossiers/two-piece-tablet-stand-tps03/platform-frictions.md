# TPS03 — platform frictions

Audience: both · Diátaxis: explanation · Kind: dated agent-experience findings

These findings concern generic authoring and execution surfaces. They are not
engineering claims about the tablet stand.

## Closeout append contract

The assembly L5 review originally returned decision parameters but not the exact
successor work-item append, including accept-only gate claims. The first appended work
item was therefore not executable and its queued run was cancelled. The review now
returns a server-derived append template and the preserved successor completed.

The static-mechanical closeout review still returns only the exact decision parameters;
the client must author the normal append envelope. Aligning it with the same
freshness-bound template would reduce AX friction without letting the agent choose a
verdict, provider or operation.

## Definition-scoped requirement projection

Workbench contained the two current unresolved requirement records, but
`project_product_inspect` initially returned an empty requirements attachment for the
selected StandBackrest definition. The join was corrected to use exact capture and
SysML identities, never labels, while preserving definition-versus-occurrence
semantics. The final API and Workbench both render the two current criteria and their
literal `pass` evaluations.

## Multi-root admission preflight

A valid two-root technical admission could not be reopened by the one-root canonical
part export. The server failed closed, but the limitation appeared only at execution.
A future preview should expose literal canonical-export eligibility without rejecting
valid multi-root analysis or pretending multi-root export exists.

## Rejected-output recovery

The FEA terminal safely retained role, byte count and digest, and published no result.
Because the rejected bytes and validator diagnostic were destroyed, the exact mismatch
cannot be proven afterward. A privacy-safe diagnostic taxonomy would still improve
future diagnosis without persisting raw solver output.

A read-only cross-check against the pinned worker contract and successful historical
meshes nevertheless isolated a platform defect: the host validator treated
`mesh.nodes` and `mesh.elements` cardinalities as maximum Gmsh identifiers. Gmsh IDs may
be offset or sparse. The generic fix keeps IDs positive integers but leaves their exact
binding to the later `mesh.inp` / `job.dat` batch comparison. This diagnosis explains
the rejection; it does not reconstruct TPS03's destroyed result or turn the failed run
into evidence. A separate server-derived activity successor completed successfully and
keeps the failed revision immutable.

## Source-template portability

The fresh TPS03 project reused root-source imports containing historical `file.tps02.*`
identifiers. Exact lowering worked, but large-scale reuse needs symbolic imports or a
versioned project-source template contract rather than project-specific identifier
rewrites.

## Workbench lifecycle and engineering-surface projection

The final project has no queued, running or waiting run. Operations now groups the
failed CalculiX revision and its successful successor through their explicit stable
activity identity and `predecessorRevisionId` chain. The live timeline renders one
`Completed` row with two revisions and two attempts; expanding it reveals the earlier
literal `Failed` attempt. The full run journal remains append-only and still exposes
both recorded runs.

The same Workbench snapshot records the FEA artifacts under authoritative system
`digital-thread` with exact producer `verify.run-fea-static-proof@3`. The Verification
facet now uses that exact versioned producer only as presentation semantics: it shows
13 CalculiX items while leaving persisted provenance unchanged. Unknown producer
versions remain unclassified.

The Operations fleet row named CalculiX is deliberately different: it describes the
declared optional `mcp-calculix` sensitivity provider, not the server-selected local
microVM used by product FEA. It must therefore remain `No project record` for TPS03.
A future Operations improvement needs a separate read-only engineering-surface
projection for the exact `digital-thread` + `verify.run-fea-static-proof@3` pair; it
must not fuzzy-join that evidence to the MCP fleet or merge base Build123d with the
Build123d sandbox.

## MCP resource-read helper

The exact file resource was successfully reread with a raw MCP `resources/read` call,
including protocol headers and `Mcp-Name`. The capability works, but the repository
still lacks a narrow read-only CLI helper parallel to the existing tools/call probe.
